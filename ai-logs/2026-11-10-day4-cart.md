  What happens when an offer changes while it's in a cart

  This is the core of the design, so it comes first.

  The browser stores only what the buyer wants. Each localStorage line holds the
  offer_id and qty, plus a small display snapshot: product name, slug, seller
  name and the price the buyer last saw. The request to /cart/quote sends only
  offer_id and qty. The snapshot is never sent, never summed and never used for
  a total. It does two jobs: it gives the cart something to show before the
  quote arrives (or when the offer no longer exists), and it lets the cart
  notice a price change.

  The server describes what is true right now. On every quote it re-reads price,
  is_active and stock (the same ProductKey::sellable scope as the store, the
  product page and the day 5 checkout, D23/D30). Nothing is reserved: quoting is
  read-only, and keys are reserved only by POST /orders (D9).

  What happens while it sits in the cart: Price goes up or down
  What the quote returns: available with the new unit_price_cents
  What the cart shows: New price in the line and the total, plus a note on the
    line: "Price changed from €24.99 to €27.99".
  ────────────────────────────────────────
  What happens while it sits in the cart: Sells out completely
  What the quote returns: sold_out, stock: 0
  What the cart shows: The line stays, dimmed, and is left out of the total.
    Buttons: "Remove" and "See other sellers" (links to the product page, where
    another seller may have stock). Checkout is disabled.
  ────────────────────────────────────────
  What happens while it sits in the cart: Partly sells out (you want 3, 1 left)
  What the quote returns: insufficient_stock, stock: 1
  What the cart shows: "Only 1 available", with "Change to 1" and "Remove"
    buttons. Left out of the total; checkout is disabled.
  ────────────────────────────────────────
  What happens while it sits in the cart: Seller withdrew the offer (is_active =
   
    false) or it was deleted
  What the quote returns: unavailable
  What the cart shows: "No longer sold by this seller", "See other sellers"
    (built from the snapshot slug), "Remove".
  ────────────────────────────────────────
  What happens while it sits in the cart: Stock comes back (a 15-minute
    reservation expired, D10)
  What the quote returns: Back to available on the next quote
  What the cart shows: The line comes back to life automatically.

  Why I don't fix the cart quantities automatically. Stock can come back without
  anyone writing anything: a reservation expires and the keys count as stock
  again (D10). If the cart silently lowered 3 to 1, or dropped a sold-out line,
  the buyer would lose what they asked for over something temporary. So the cart
  keeps the buyer's wish, the quote reports reality, and checkout is enabled
  only when every line can be bought in full. That way the total on screen is
  always exactly what checkout would charge.

  When the price-change note appears. The snapshot price means "the last price
  this buyer was shown". When a quote shows a different price, the cart displays
  the note and then updates the snapshot to the new price. The note stays
  visible for the rest of that visit and doesn't come back after a reload,
  because the buyer has now seen the new price. Both directions get a note,
  since a price drop is good news too.

  How fresh the quote is. On the cart page the quote is always treated as stale,
  so it refetches on page load, when the window regains focus (TanStack Query's
  default), and when a quantity changes. Previous data stays visible while the
  next quote loads, and superseded requests are aborted (the same pattern as
  D29).

  The gap the quote can't close (day 5, recorded now). A price can still change
  in the seconds between the last quote and clicking "Checkout". On day 5, POST 
  /orders will also receive expected_total_cents, the total the buyer saw. If
  the server's recalculated total differs, it answers 409 price_changed with a
  fresh quote and creates nothing. Selling out in that gap is already handled by
  the planned 409 Out of stock. Either way the buyer is never charged an amount
  they weren't shown.

  Backend: POST /api/cart/quote

  It's a POST because the input is a list, but it has no side effects. It is
  public, with no auth (D8).

  Request, validated in CartQuoteRequest:
  { "lines": [ { "offer_id": 12, "qty": 2 }, { "offer_id": 40, "qty": 1 } ] }
  - lines: required, 1 to 50 entries.
  - offer_id: integer, distinct (a duplicate offer gets a 422; the frontend
    merges duplicates before sending).
  - qty: integer from 1 to 10.

  An offer ID that doesn't exist is not a validation error. A cart can outlive
  an offer, so that line comes back as unavailable instead.

  Response: lines come back in the same order as the request (the order they
  were added).
  { "data": {
    "lines": [{
      "offer_id": 12, "qty": 2, "status": "available", "stock": 14,
      "unit_price_cents": 1999, "original_price_cents": 2499,
  "discount_percent": 20,
      "line_total_cents": 3998,
      "product": { "slug", "name", "image_url", "platform", "region" },
      "seller": { "id", "name", "rating" }
    }],
    "total_cents": 3998, "currency": "EUR", "can_checkout": true
  }}
  - status is one of available, insufficient_stock, sold_out or unavailable.
  - line_total_cents is set only for available lines (null otherwise), and
    total_cents sums only those lines.
  - can_checkout is true when every line is available.
  - For an unavailable line, the price, product and seller fields are null when
    the offer no longer exists.

  Code layout, the same layering as the catalog:
  - Services/Cart/CartQuoter: one query for the requested offers (active or
    not), eager-loading seller and product with its platform and region, with
    withCount('keys as stock', sellable($now)). The status and total logic is
    plain PHP. It returns a small CartQuote value object. On day 5, POST /orders
    reuses the same class, so the cart total and the order total can't come
    from two different implementations.
  - CartController@quote (thin), CartQuoteResource, and a route in api.php.

  Tests (feature tests on PostgreSQL):
  - A price field sent by the client is ignored.
  - The total sums only available lines.
  - One test for each of the four statuses, plus the boundary stock == qty →
    available.
  - An expired reservation counts as stock; an active one doesn't (proves the
    shared scope is used).
  - An inactive offer and a missing offer both return unavailable.
  - The request order is preserved.
  - Validation: qty 0, qty 11, duplicate IDs, 51 lines, non-integers, missing
    lines.
  - The query count stays constant as lines are added (no N+1).

  As on day 4, I'll break each rule on purpose to confirm a test fails.

     Eneba also caps it.

     shown), for both rises and drops.
