  1. Where the token lives in the browser, and what that means

  Recommendation: keep D7's choice. The token goes in localStorage under 
  intersheba.auth.token, and nothing else is stored there. The user's details
  are fetched from GET /auth/me.

  Why each option is or isn't safe:

  Option: localStorage (chosen)
  What JavaScript can do with it: Any script on our page can read it
  Survives a reload or new tab: Yes
  Works across our two sites: Yes
  ────────────────────────────────────────
  Option: sessionStorage
  What JavaScript can do with it: Any script on our page can read it
  Survives a reload or new tab: No new tabs; gone when the tab closes
  Works across our two sites: Yes
  ────────────────────────────────────────
  Option: Memory only
  What JavaScript can do with it: Harder to steal
  Survives a reload or new tab: No: signed out on every refresh
  Works across our two sites: Yes
  ────────────────────────────────────────
  Option: HttpOnly cookie
  What JavaScript can do with it: Scripts can't read it
  Survives a reload or new tab: Yes
  Works across our two sites: No. *.vercel.app and *.onrender.com count as
    different sites, so it becomes a third‑party cookie that Safari and Firefox
    block (D7)

  What this means for security:

  - The real risk is XSS (cross-site scripting). If an attacker ever gets their
    own script to run on our page, it can read the token, send it to their
    server and use it from anywhere. It stays usable until it expires or the
    user logs out.
  - The limits on that risk:
    - Tokens expire after 7 days (D18).
    - Logout deletes the token row on the server, so it stops working at once.
    - The database stores only a SHA‑256 hash of each token (D18), so a leaked
      copy of the table can't be used to sign in.
  - HttpOnly isn't a full fix either. With a cookie, injected script still can't
    read the token. But it can still send requests as the user while the page
    is open. HttpOnly stops the token being stolen for later; it does not stop
    XSS. The real defence is preventing XSS:
    - React escapes everything it renders.
    - We never use dangerouslySetInnerHTML.
    - Banner links are filtered to same-site paths (D32).
  - The upside of localStorage: no CSRF (cross-site request forgery). The
    browser never attaches the token by itself. Only our code adds
    Authorization: Bearer …, so a forged request from another site arrives
    without credentials. That's why CORS can keep supports_credentials: false.
  - What a production build would do instead: put the API behind a Vercel
    rewrite (/api/* → Render). The cookie becomes first-party, so an HttpOnly
    cookie plus CSRF protection becomes possible. I'll record that as the
    trade-off, not build it.
  - Optional extra: a Content-Security-Policy header in vercel.json (for example
    script-src 'self'). It stops injected inline scripts from running and
    limits which hosts the page can talk to. See question 1.

  2. Backend

  - Routes:
    - POST /auth/register returns 201 {token, user}.
    - POST /auth/login returns 200 {token, user}.
    - POST /auth/logout returns 204.
    - GET /auth/me returns the current user.
    - The leftover /user route is removed.
  - Code layout: AuthController (thin), RegisterRequest, LoginRequest and
    UserResource (id, name, email; the password never appears). There's no
    service class, because there's no logic to reuse; it's Laravel's hashing

  - Sanctum settings:
    - expiration = 10080 minutes (D18).
    - guard = [], so a bearer token is the only way to authenticate. Today
      Sanctum tries a session first, and this app has no sessions.

      IP. Both answer 429.

      load balancer.

  Where the token lives, and what that means

  - Where: localStorage, key intersheba.auth.token. Only the token is stored;
    the user's details come from GET /auth/me.
  - The risk: any script running on our page can read the token. So an XSS bug
    could steal it and use it from anywhere for up to 7 days, or until the user
    signs out (sign-out deletes it on the server at once).
  - Why an HttpOnly cookie wouldn't fully fix that: injected script can't read
    the cookie, but it can still send requests as the user while the page is
    open. HttpOnly only stops the token being carried off for later. The real
    defence is preventing XSS:
    - React escapes everything it renders.
    - There's no dangerouslySetInnerHTML.
    - The CSP will help once it's merged.
  - The upside: no CSRF. The browser never attaches the token by itself; only
    our API client adds it.
  - The production alternative: proxy the API through Vercel so a first-party
    HttpOnly cookie becomes possible. It's recorded in D33, not built.

  Backend

  - Endpoints: register, login, logout (signs out this device only) and "who am
    I".
  - Settings: tokens expire after 7 days, and a bearer token is the only way to
    authenticate.
  - Emails are lowercased. PostgreSQL's unique index is case-sensitive, so
    otherwise Demo@example.com could become a second account.
  - Passwords are limited to 72 bytes, not characters. Bcrypt silently ignores
    everything after byte 72.
